# 0001. Stack and architecture: a TypeScript monolith on Next.js with Postgres

**Date**: 2026-10-12
**Status**: In Progress

## Summary

Movix is built as one TypeScript web app (a monolith, meaning one codebase and one thing to deploy) on Next.js. Its data and its movie embeddings (numbers that let search match a mood) live together in one Postgres database on Neon, and accounts use the Better Auth library. This keeps a solo, few week build to the fewest moving parts while leaving room for vibe search. Catalog source, embedding model, and reasons model are deliberately left to their own feature specs.

## Decision

**Chosen option**: Option 1: One TypeScript monolith on Next.js, Postgres with pgvector on Neon, Drizzle, Better Auth, Vercel

Build Movix as a single Next.js (App Router) application in TypeScript on Node.js with pnpm, one package in one repo, backed by Postgres with the pgvector extension on Neon, accessed through Drizzle, with Better Auth for email and password accounts, deployed on Vercel.

**Implementation skills**: `nextjs-app-router-patterns` (`wshobson/agents`, `.agents/skills/nextjs-app-router-patterns/`) · `vercel-react-best-practices` (`vercel-labs/agent-skills`, `.agents/skills/vercel-react-best-practices/`) · `next-dev-loop` (`vercel/next.js`, `.agents/skills/next-dev-loop/`) · `deploy-to-vercel` (`vercel-labs/agent-skills`, `.agents/skills/deploy-to-vercel/`) · `neon-postgres` (`neondatabase/agent-skills`, `.agents/skills/neon-postgres/`) · `drizzle-orm-patterns` (`giuseppe-trisciuoglio/developer-kit`, `.agents/skills/drizzle-orm-patterns/`) · `better-auth-best-practices` (`better-auth/skills`, `.agents/skills/better-auth-best-practices/`) · `tailwind-design-system` (`wshobson/agents`, `.agents/skills/tailwind-design-system/`) · `zod` (`pproenca/dot-skills`, `.agents/skills/zod/`)

## Proposed stack

| Layer | Choice | Reason |
|---|---|---|
| Application shape | Single full stack web app, one deployable (monolith) | One builder and a small user count need the simplest thing to build and debug; nothing is extracted until a real bottleneck forces it. (basis: monolith first for small teams) |
| Language | TypeScript, strict mode | One language and shared types from database to swipe UI. |
| Runtime and package manager | Node.js on the current LTS major, pinned in `engines`, `.nvmrc`, and the Vercel project setting at scaffold time, with pnpm pinned through the `packageManager` field | Works with every host and library here; pnpm gives fast, strict installs, and pinned versions keep local and production the same. |
| Repo shape | One package at the repo root | No second deployable exists; split into workspaces only if one appears. |
| Framework | Next.js, App Router (16.x at time of writing) | Server rendered pages and server endpoints in one app; largest ecosystem for a solo builder. |
| Client and server calls | Server components for reads, Server Actions for mutations, route handlers for file upload and search endpoints | Built into the framework, typed, and no extra API layer to maintain. |
| Primary database | Postgres with pgvector on Neon | Relational data and embeddings in one store, so vibe search needs no second system; plain Postgres keeps the data portable. (basis: a relational database as the default primary store) |
| Data access and migrations | Drizzle ORM with Drizzle Kit migrations | SQL shaped, typed, light at runtime, supports vector columns; raw SQL through Drizzle's `sql` template for ranking queries where the query builder gets in the way. |
| Postgres driver | `pg` (node-postgres) through `drizzle-orm/node-postgres`, for local and production | Neon's HTTP driver cannot run interactive transactions, which Better Auth and imports need, and cannot reach the local container. |
| Connection strings | Neon pooled URL as `DATABASE_URL` for the app; Neon direct URL as `DATABASE_URL_UNPOOLED` for migrations and scripts | Pooled connections suit serverless request handlers; migrations need a direct connection. |
| Migrations | `drizzle-kit generate` with committed SQL, applied by hand or in CI before deploy, never in the Vercel build. The first migration runs `CREATE EXTENSION IF NOT EXISTS vector` | A reviewable history, and drizzle-kit does not create extensions itself. |
| Local development database | Postgres with pgvector via `docker compose`, using the `pgvector/pgvector` image on the same Postgres major version as the Neon project | Works offline, matches production, and cannot touch production data. |
| Auth | Better Auth (self hosted library), latest stable line (1.7.7 at time of writing) with a range that never resolves below 1.6.22 | Accounts stay in your app and your database, and password handling is a proven library, not hand rolled. (basis: use a proven auth library) |
| Auth tables | Generated by the Better Auth CLI into the Drizzle schema file, so drizzle-kit owns every table; the ID type stays with feature #3 | One migration history for all tables, and no second schema tool. |
| Styling | Tailwind CSS | Fast responsive layout and a good fit with server components; the visual language and base components are decided in feature #5. |
| Validation | Zod | One schema checks form input, uploads, API input, and environment variables, and gives the type. |
| Source layout | `src/` with `app/`, `db/` (client and schema), `auth/`, `lib/`, an `@/*` import alias, and `src/env.ts` as the Zod parsed environment | Matches the nested `src/auth` convention the skills expect and keeps configuration validated in one place. |
| Next.js caching | Cache Components off for Release 1 | Every personal page is dynamic; revisit only for public catalog pages. |
| Background work | None in Release 1: catalog loading and embedding run as manual `tsx` scripts in `scripts/` that use the same Drizzle client against the direct URL and the shared env module; ratings import is parsed during the request | No measured need for a queue yet. (basis: add queues only after measuring a bottleneck) Revisit in features #4 and #12. |
| Hosting | Vercel | No adapter for Next.js, and request time limits are roomy enough for ranking. Request body size caps apply to uploads (feature #12), and free plan terms apply; see Consequences. |
| Regions | Vercel function region and Neon region set together | Ranking makes several queries per request, so cross region round trips add up. |
| Deploy path | GitHub repository with Vercel's Git integration; `main` is production | Simplest hands off deploy for one builder. The folder is not a git repo yet, so the scaffold initializes one. |
| Environments | Production on Neon's main branch, local on the container, Vercel previews on one long lived Neon preview branch | Previews must never touch production data. |
| Observability | Decided in feature #10 | Analytics and error monitoring are their own decision. |
| Lint, format, test tooling | Decided by `/audit` and `/develop tooling` in feature #2 | Captured from the real scaffold, not guessed. |

**Left to their own feature specs** (this stack only guarantees a vector capable database and a server runtime for them):

- Movie catalog source and its license terms: feature #4
- Component primitives and visual language: feature #5
- Session length, password rules, and reset: feature #6
- Route protection (Next.js 16 uses `proxy.ts` where older versions used middleware, per the cross check; verify against the installed Next.js skills), Better Auth environment variables and trusted preview origins, and rate limit storage (it must use the database, since the default memory store does nothing across serverless instances): feature #6
- Reasons generation model: feature #11
- CSV parsing approach: feature #12
- Embedding model for vibe search: feature #13

## Consequences

**Positive**:
- One language, one repo, one deploy, so a solo builder carries the least overhead.
- Relational data and vector search share one database and one backup story.
- Plain Postgres and a library based auth keep user data portable and out of a vendor system.

**Negative / tradeoffs**:
- Neon's free plan scales to zero after 5 idle minutes, so the first request after a quiet period is slow, and storage is capped at 1 GB. Embeddings for a large catalog must be sized against that cap in feature #13.
- Vercel's free plan is, from my knowledge and not rechecked, for non commercial use. That is fine while Movix is free and must be revisited before any monetization.
- Next.js conventions (server components, caching) move quickly, so the installed skills and current docs should be consulted rather than memory.
- Request body size caps (about 4.5 MB on Vercel and 1 MB by default for Server Actions, from the reviewer's knowledge and not verified) bound a ratings upload. Uploads go through a route handler, and feature #12 owns the cap and accepts only the ratings file. Work that outgrows a request moves to scripts or a job runner later.
- A Neon cold start can stack on a Vercel cold start, so the first feed load after a quiet period may take a few seconds. Feature #9 needs a loading state for it.

**Neutral**:
- Better Auth must never resolve below 1.6.22 (an advisory for its magic link and email code plugins was fixed there); those plugins are not used. Start from the latest stable.
- Vercel's free plan runs scheduled jobs at most once a day (from the reviewer's knowledge, not verified), which is consistent with having no queue in Release 1.
- Constraints the build must honor: TypeScript strict, all database access through the one Drizzle client (raw SQL only via its `sql` template), all external input and environment variables validated with Zod, secrets only in environment variables, database access only in server code.
- The scaffold installs only the runnable skeleton (framework, language, runtime). Each later feature installs its own dependencies when built.
